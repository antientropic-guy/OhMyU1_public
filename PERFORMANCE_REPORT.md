# Отчёт по ускорению solver и U(1)-MPS

## Методика измерений

Измерения выполнены на Julia 1.12.5 с четырьмя потоками. Время JIT-компиляции
не включалось: перед измеряемым запуском выполнялся один прогрев с теми же
параметрами. Для воспроизводимости использовались фиксированные `seed` и
RNG-aware sampler.

Основной сокращённый benchmark повторяет пользовательский сценарий:

```julia
n = 10
A = assignment_matrix(n)
b = ones(Int, 2n)
Q = random_bilinear_form(Random.Xoshiro(100), n^2, 1.0, 7)
problem = OptimizationProblem(A=A, b=b, cost_function=x -> dot(x, Q * x))
sampler = (rng, X) -> fill_assignment_vectors!(rng, X, n)
params = SolverParams(NUM_GLOBAL_ITER=5, KEEP_NUM_WORST=0.0,
                      LEARNING_RATE=0.05)
solve(problem, sampler, params, "weighted rank";
      parallel=true, print_stats=false, rank_weight=0.1, seed=100)
```

Готовый воспроизводимый runner находится в `scripts/benchmark_solver.jl`:
`julia --project=. -t 4 scripts/benchmark_solver.jl 10 5 3`.

## Результат

| Сценарий | До | После | Изменение |
|---|---:|---:|---:|
| `n=10`, 5 итераций, прогретый | 7.233 с | медиана 5.045 с | в 1.43 раза быстрее |
| Выделенная память в том же запуске | 2.577 GiB | 1.269 GiB | −50.8% |
| `n=16`, 1 итерация, прогретый | — | медиана 8.922 с | контроль масштабирования |

Три последовательных измерения нового варианта для `n=10` дали 5.045,
5.070 и 4.875 с. Два измерения для `n=16` дали 9.017 и 8.827 с. Ранее
полученное время 27.49 с для `n=16` включало JIT-компиляцию, поэтому оно не
используется как корректная база для вычисления ускорения.

## Что изменено

### Sampling MPS

Раньше для каждого образца, сайта и допустимого значения переменной выполнялся
поиск блока в
`Dict{Tuple{Vector,Vector,Vector},...}`. Каждый такой поиск заново хешировал
несколько векторов зарядов. Теперь перед sampling один раз строится таблица

```text
текущий левый заряд -> вектор амплитуд по значениям x.
```

В основном цикле остаётся один поиск по текущему заряду на сайт. Убраны также
временные векторы на каждый образец и обёртка `StatsBase.Weights`; выбор из
дискретного распределения выполняется линейным проходом по малому домену.
Результат остаётся независимым от расписания потоков.

### Графовое расстояние

Пусть `q₀=b` и

```math
q_j = q_{j-1} - A_{:,j}x_j.
```

Используемое расстояние равно числу позиций `j`, для которых `q_j` отсутствует
в множестве ранее наблюдавшихся зарядов. Для каждого столбца `A` теперь один
раз сохраняются только ненулевые пары `(row, value)`, а при `x_j=0` обновление
полностью пропускается. `Channel`-pool заменён одним буфером на Julia thread.

Арифметическая часть меняется с `O(N d m)` на
`O(N sum_j nnz(A[:,j]) [x_j != 0])`, где `N` — число образцов, `d` — число
переменных, `m` — число ограничений. Для assignment sample ненулевы только `n`
из `n²` переменных, и каждый соответствующий столбец имеет два ненулевых
элемента. Однако проверка принадлежности `Vector` множеству всё ещё хеширует
вектор длины `m` на каждом сайте, поэтому фактический выигрыш этой части
умерен: на 20 000 образцов при `n=16` измерено 0.409 с против 0.360 с
(в 1.14 раза). Следующий принципиальный шаг здесь — компактный/инкрементальный
ключ заряда, а не дальнейшая распараллелизация `Dict`.

### Аналитические LQ и SVD

Для невырожденной левой связи блок LQ является строкой `a`. Поэтому

```math
a = LQ, \qquad L=[\lVert a\rVert_2],\qquad
Q=a/\lVert a\rVert_2.
```

В общей ортогонализации все блоки с одинаковым левым зарядом рассматриваются
как одна склеенная строка. Вычисляется её норма
`sqrt(sum(norm(block)^2))`; блоки делятся на неё, а множитель поглощается
предыдущим core. Это точно та же gauge-трансформация без тысяч маленьких
вызовов LAPACK. Нулевые/вырожденные случаи сохраняют общий путь.

При sweep большинство merged blocks имеют размеры `1×1`, `1×2`, `2×1` или
`2×2`. Для первых трёх ведущая сингулярная тройка получается нормировкой
вектора. Для `2×2` максимальное сингулярное значение вычисляется как корень из
максимального собственного значения `B'B`:

```math
\lambda_+ = \frac{g_{11}+g_{22}+
\sqrt{(g_{11}-g_{22})^2+4g_{12}^2}}{2},\qquad \sigma_1=\sqrt{\lambda_+}.
```

Обычный `svd` оставлен для остальных размеров. Тест сравнивает ведущую
rank-one реконструкцию с LAPACK.

### Обучение

Массив link charges теперь вычисляется один раз на полный right/left sweep, а
не дважды. Проверки ненулевого столбца `A` вынесены из внутреннего цикла по
образцам. Boltzmann weights используют одно вычисление cost на образец вместо
двух.

## Проверка идеи с локальными словарями и merge

Для репрезентативного слоя `n=16`, 1000 training samples и 972 уникальных
зарядов сравнивались:

1. один последовательный `Dict{Vector{Int},Nothing}`;
2. по одному локальному словарю на поток, затем последовательный `merge!`.

Среднее по 100 построениям: 0.606 мс против 0.670 мс. Вариант с merge оказался
на 10.5% медленнее и в код не включён.

При ожидаемой `O(1)` вставке последовательное построение имеет ожидаемую
сложность `O(B)`. Локальное построение имеет parallel span около `O(B/p)`, но
последовательное слияние требует `O(sum_t U_t)` вставок. При большом числе
различных ключей это снова `O(B)` в критическом пути; при ключах, повторённых
во всех локальных таблицах, объём merge может достигать `pU`. На текущих
размерах стоимость scheduling, локальных таблиц и повторного хеширования выше
выигрыша. Безопаснее распараллеливать независимые bonds/cores, если эта стадия
станет доминирующей на более крупных данных.

## Корректность

Автоматически проверяются:

- совпадение аналитического tiny-SVD с LAPACK;
- сохранение амплитуд MPS после ускоренной ортогонализации;
- реконструкция `L*Q` исходных блоков;
- точное совпадение нового и старого графового расстояния;
- допустимость сгенерированных assignment samples;
- идентичность serial/parallel sampling при одинаковом seed;
- полная повторяемость `solve`.
